## 1. Why this research and what "fit" means here

CleargateFinance's recent work (per `git log` on `feature/agent-credentials`) is building:

- `feat(crypto): agent API keys, a handle plus a secret` — first-party issuance of API credentials to AI agents
- `feat(account): connect agents and issue rotatable credentials` — binding agents to accounts with rotation
- `feat(account): open a run to group an agent's payments` — grouping an agent's payments into a "run," implying limits/auditing/settlement semantics
- `test(account): cover agent credential issue, rotation and revocation`

Combined with a `kyc_status` column in `migrations/000004_identity.up.sql`, this reads as: **a regulated fintech platform where AI agents act as first-class principals that hold rotatable credentials and make payments on behalf of KYC'd accounts, grouped into auditable "runs."**

The question this document answers: should Cleargate build its own key-custody and signing layer end-to-end, or adopt Turnkey or Privy underneath its existing agent-credential/run system — and if so, which one, and how much of Cleargate's own credential-rotation/revocation and "run" logic would the vendor replace vs. sit beneath?

**Evaluation criteria** (as specified for this research):
1. Core architecture (custody model, agent/programmatic key usage)
2. Security model (key location, non-extractability, attestation, audits/certifications)
3. Credential/session lifecycle (issuance, rotation, revocation, scoping)
4. Policy/permissioning engine (spend limits, counterparty/contract allowlists, velocity limits — maps to Cleargate's "run" concept)
5. SDKs and integration surface (languages, Go support specifically, self-hosted vs. hosted-only)
6. Compliance posture (KYC/AML tooling, licensing, data residency, certifications)
7. Pricing model (as published, sales-gated pricing flagged)
8. Target use-case fit (institutional/programmatic vs. consumer-embedded positioning, verified from current marketing/docs rather than assumed)

**Method:** Primary sources only — each vendor's own docs, whitepaper, blog, security/trust pages, and pricing pages. Web search was used only to *locate* the correct primary URLs; every claim below is attributed to a specific fetched page. Where I could not reach or confirm a claim on a primary page, it is flagged explicitly rather than stated as fact (see §6, "Verification gaps").

## 2. Side-by-side comparison

| Criterion | Turnkey | Privy |
|---|---|---|
| **1. Core architecture** | Custody runs on AWS Nitro Enclaves via a proprietary enclave OS ("QuorumOS"). Five specialized enclave apps: **Policy Engine** (auth/authz, emits signed "Rulings"), **Notarizer** (tamper-evident org-data storage), **Signer** (key generation/signing, key material never exists in plaintext outside the enclave), **Parser** (decodes tx metadata for policy evaluation), **TLS Fetcher** (attested outbound HTTP). Organizations start with a single-party "Root Quorum" and can grow to multi-party (e.g., 2-of-3) quorums. Agents are modeled as first-class **Users** with their own API keys, distinct from end-users. [whitepaper.turnkey.com/architecture](https://whitepaper.turnkey.com/architecture), [docs.turnkey.com/security/our-approach](https://docs.turnkey.com/security/our-approach) | Custody also runs on AWS Nitro Enclaves, but the key-protection model is **2-of-2 Shamir's-Secret-Sharing** rather than a quorum of enclave apps: an **enclave share** (decryptable only inside the TEE) and an **auth share** (held by Privy, released only on valid user authentication). The two shares are combined *in-memory, transiently* inside the enclave to reconstruct the key for a single signature, then discarded. Agents are supported via two explicit "control models" — agent-owned wallets, or user-owned wallets with a delegated agent signer (see row 3). [docs.privy.io/security/wallet-infrastructure/architecture](https://docs.privy.io/security/wallet-infrastructure/architecture) |

Remote attestation is performed at every deploy before secrets are provisioned into the enclave; "no single developer... can alter or deploy enclaves, or reconstruct core secrets." Reproducible/deterministic builds are published so the enclave code can be independently verified. **SOC 2 Type II** certified. Independent audits from **Distrust, Cure53, Trail of Bits, and Zellic**. [docs.turnkey.com/security/our-approach](https://docs.turnkey.com/security/our-approach), [www.turnkey.com/security-by-turnkey](https://www.turnkey.com/security-by-turnkey) | Same TEE non-extractability principle, reinforced by key sharding (no single share, including the TEE's own share, is sufficient alone). **SOC 2 Type II** — most recently renewed with an audit window of Nov 1, 2025–Feb 1, 2026 per Privy's own blog. | **3. Credential/session lifecycle** | Agents are provisioned as "Delegated Access" (DA) **Users** authenticated by **P-256 API keys**, distinct from human end-users. A DA user "has zero permissions by default" — all capability must be explicitly granted via policy. Turnkey's own guidance: rotate API keys regularly, prefer short-lived keys, store keys in HSMs/secret managers, and grant the DA user "permission to delete itself for fast remediation if compromised" (i.e., self-revocation). Consensus/co-signing (human + agent, or agent + agent) is supported via policy expressions (`approvers.any(...)`). [docs.turnkey.com/features/policies/delegated-access/agentic-wallets](https://docs.turnkey.com/features/policies/delegated-access/agentic-wallets) | Two distinct models: **(a) agent-owned/developer-controlled wallets**, where the agent "holds the credential needed to trigger signing" directly; **(b) delegated signing**, where a human/user grants the agent "an authorization key with a defined scope via policies," revocable by the user at any time. A separate "Agent CLI" flow uses a one-time human browser approval followed by **short-lived ephemeral signing keys**, sessions capped at 30 days with automatic rotation, so agent processes never hold long-lived private-key material. [docs.privy.io/wallets/overview/solutions/agent-wallets](https://docs.privy.io/wallets/overview/solutions/agent-wallets) |

Multi-party consensus rules are expressible (human+agent approval for high-value actions). This maps closely onto a "run" concept: a run could be represented as a scoped policy set applied to a DA user for the run's duration. [docs.turnkey.com/features/policies/delegated-access/agentic-wallets](https://docs.turnkey.com/features/policies/delegated-access/agentic-wallets), [whitepaper.turnkey.com/architecture](https://whitepaper.turnkey.com/architecture) | Policy engine enforces guardrails "cryptographically, not just as prompt instructions the agent can ignore": token/chain restrictions, per-transaction caps, **time-window (velocity) limits**, recipient/contract allowlists, and human-in-the-loop approval workflows. ## 3. Fit for CleargateFinance

**What both vendors would replace vs. what Cleargate keeps:**

Cleargate already has (per the git log) its own layer for: (a) issuing agent API credentials (handle + secret), (b) connecting agents to accounts, (c) rotating and revoking credentials, and (d) grouping an agent's payments into a "run." Both Turnkey and Privy operate *one layer below* that: they own **private-key custody and the cryptographic signing operation**, plus their own credential/session primitives (Turnkey's "Delegated Access" API keys; Privy's agent authorization keys / ephemeral CLI sessions) and their own policy engines for spend limits and counterparty allowlists.

This means adopting either vendor would **not eliminate** Cleargate's agent-credential system — the two layers are complementary, not redundant, *if* Cleargate's credentials are used to authenticate to Cleargate's own API and the vendor's credentials/keys are provisioned and scoped by Cleargate's backend per agent, effectively nesting the vendor's agent-signing identity inside Cleargate's own agent/account model. What it *would* replace is any Cleargate-built (or planned) private-key generation, storage, and raw-signing code — which is exactly the piece that is highest-risk and hardest to get right in-house (this is the component both vendors gate behind TEEs, attestation, SOC 2, and multiple independent audits).

The "run" concept maps well to both vendors' policy engines: a run's spend cap, allowed counterparties, and lifetime could be expressed as a scoped Turnkey Delegated-Access policy or a scoped Privy agent-wallet policy, created at run-open time and expired/deleted at run-close — pushing enforcement down into the signing layer instead of Cleargate's application layer trusting itself to check limits before calling a raw signer. That's a meaningful defense-in-depth upgrade over an app-layer-only limit check.

**Compliance/KYC angle:** the `kyc_status` column suggests Cleargate itself owns the identity/KYC determination and probably a KYC vendor integration — neither Turnkey nor Privy is a KYC provider or a licensed VASP; both are explicit that compliance/AML/licensing is the customer's responsibility, with Privy naming specific analytics-provider integrations (Chainalysis/Elliptic/TRM) it can plug into and Turnkey being vaguer (audit-trail generation, not KYC/AML itself). Neither changes Cleargate's regulatory posture; both would sit underneath it as a signing/custody backend.

**Go backend fit:** both vendors publish an official Go SDK (`tkhq/go-sdk` for Turnkey, `privy-io/go-sdk` for Privy), so language fit is a wash — this is not a differentiator.

**Architectural fit specifically for *agents as principals*:** Turnkey's docs treat agents as a first-class "User" type with policy-scoped API keys from the ground up, and its policy engine is described as evaluating "every agent action" inside the enclave — the framing throughout Turnkey's docs is closer to what Cleargate needs (programmatic, non-interactive, many-agents-per-org, consensus-approvable). Privy's docs present two parallel models (agent-owned vs. delegated-from-a-user) that read as retrofitted onto a fundamentally end-user/consumer-auth architecture (its core product is still "embedded wallets" for human end users logging in with email/Google/passkey) — workable, but Cleargate would be adopting the less-traveled path of Privy's stack rather than its center of gravity.

## 4. Recommendation

**Lean toward Turnkey, but validate two things with the vendor directly before committing** (see gaps below): (1) actual Enterprise pricing at Cleargate's expected signature volume, and (2) confirmation of institutional/regulated-fintech reference customers, since none were independently verified in this pass beyond the vendor's own marketing claims.

Reasoning:
- Turnkey's architecture is agent-native from the ground up (DA users, zero-default-permission model, policy evaluated inside the enclave, self-revocation pattern) — this is the closest conceptual match to Cleargate's existing agent-credential-and-run model, and it's easiest to reason about "what does the vendor replace vs. what does Cleargate keep" cleanly: vendor owns keys+signing+policy-enforcement, Cleargate owns agent identity/account linkage/run bookkeeping/KYC.
- Turnkey's positioning (institutional/treasury/payments first, AI agents as a named top-level segment) is a closer match to a regulated-fintech, non-consumer-embedded product than Privy's, whose primary documented product surface is still consumer embedded wallets (email/social login), with agent/fintech support layered on more recently.
- Security posture is roughly comparable (both SOC 2 Type II, both AWS Nitro Enclaves, both multiple independent pentest firms) — this is **not** a deciding factor either way.
- Pricing structures are comparable in shape (free tier → flat+per-signature → custom enterprise) and both gate real enterprise numbers behind sales, so pricing is also not a clean deciding factor without a live quote.

**"It depends" factor that could flip this:** if Cleargate anticipates needing consumer-facing end-user embedded wallets *in addition to* agent wallets (e.g., letting Cleargate's own human customers hold self-custodial wallets, not just agents), Privy's stronger track record and product depth on the human-embedded-wallet side becomes relevant and might argue for Privy or a dual-vendor approach. Based on the git log and the "run"/agent-credential framing, that does not appear to be the near-term priority, which is why this recommendation leans Turnkey.

## 5. Verification gaps / claims not fully confirmed against primary sources

- **Privy Trust Center content** (`trust.privy.io`) could not be extracted in this pass — the page appears to require interaction/login-gated detail beyond what a static fetch returns. SOC 2 and pentest-firm claims are sourced instead from Privy's `/security` page and blog post, which is a primary source, but the Trust Center itself (which likely hosts the actual SOC 2 report and pentest summaries) was not independently opened. **Action:** request access directly if a decision hinges on it.
- **Enterprise pricing (both vendors)** is explicitly sales-gated ("Custom," "as low as $0.0015/signature" for Turnkey, "starting at $0.001/signature" for Privy) — these are floor/teaser numbers from public pricing pages, not confirmed quotes. **Action:** get a real quote from both before a budget decision.
- **Turnkey's KYC/AML/compliance depth** is thinner in primary sources than Privy's — Turnkey's compliance blog post explicitly does not mention KYC/AML/transaction-monitoring integrations the way Privy's `/fintech` page names Chainalysis/Elliptic/TRM Labs. This may reflect a real difference, or may simply mean Turnkey documents it elsewhere (e.g., a solutions page not surfaced by search). **Action:** ask Turnkey directly whether/how it integrates with KYC/AML/screening vendors.
- **Regulatory licensing status** of either vendor (are they themselves licensed as a money transmitter, VASP, etc., anywhere) was not found on either primary site — both frame compliance/licensing as the customer's responsibility, and neither claims to hold licenses itself. This is reported as an absence, not confirmed as "neither is licensed anywhere" (i.e., unverified either way).
- **Independent/reference-customer validation** of either vendor's claims (uptime, "SOC 2 audit window," "trusted by fintech leaders," audit firm engagement scope) was not performed — all such claims trace to the vendor's own marketing/blog copy, not to the audit reports themselves or to customer-side confirmation.
- **Turnkey's non-custodial/"unlike MPC" framing** (from the homepage) is marketing language positioning enclave-based custody against MPC-based approaches (which is what Privy actually uses in combination with TEEs); this is a competitive claim from one vendor about the category, not independently adjudicated in this research, and is presented in the table as "what Turnkey says," not as an established technical superiority claim.
- **Go SDK maturity/production-readiness** was confirmed to *exist* for both (package pages on pkg.go.dev, docs pages), but this research did not evaluate code quality, API completeness, or open issues in either repo.
